# ADR-002: Defer Fabric to Phase 6, build Phases 1-5 locally

**Status:** Accepted
**Date:** 2026-07-24
**Amended:** 2026-07-24

## Context
Fabric trial capacity is 64 CU for 60 days, granted once per tenant and
non-renewable. Once started, the clock runs whether or not the capacity is
in use.

Phases 1 through 5 are ingestion, cleansing, dimensional modelling, semantic
modelling and report design. None strictly require Fabric compute to design
and validate: transformation logic can be written in ANSI SQL against Parquet
locally, Power BI Desktop is free and runs the full semantic model and report
experience, and star schema design is a modelling exercise, not a compute one.

The capabilities that genuinely require Fabric are concentrated later:
Direct Lake, Eventstream, Eventhouse, Activator, deployment pipelines,
capacity metrics, OneLake shortcuts and workspace governance.

## Decision
Profile and prototype Phases 1-5 locally using DuckDB and Python for the data
layers, and Power BI Desktop for the semantic layer and reports. Activate the
Fabric trial at Phase 6, when the Fabric-specific capabilities become
unavoidable.

## Consequences

**Positive**
- The 60-day window covers the phases that actually consume it.
- Phase 1 cost $0 and produced ANSI SQL that transfers to the Fabric
  Warehouse and to Spark SQL with minimal change.
- Local iteration is faster than cloud iteration, so exploratory work happens
  where the feedback loop is shortest.

**Negative**
- The Bronze ingestion originally planned for Phase 1 — metadata-driven Data
  Factory pipeline, control table, ForEach, watermark incremental load,
  Dataflow Gen2 — is deferred, not delivered. Required for DP-700 and built
  once capacity is live. The traceability matrix reflects this as in-progress.
- The local Python download script is throwaway; it becomes a Copy activity.
  What transfers is the idempotence principle, as a watermark table.
- DuckDB is not Spark. Join skew, small-file behaviour, partition pruning and
  V-Order effects differ and must be re-measured. Local performance claims are
  provisional.
- Delta-specific operations (MERGE INTO, OPTIMIZE, VACUUM, time travel) cannot
  be exercised locally and are unproven until Phase 6a.

## Amendment — 2026-07-24
Phase 6 as originally scoped absorbs the entire deferred Fabric workload plus
the real-time layer. That is too much for a single phase inside a 60-day
window. Phase 6 is therefore split:

| Phase | Scope | Target days |
|---|---|---:|
| 6a — Migration | Trial activation, Lakehouse and Warehouse, metadata-driven Bronze pipeline with control table, ForEach and watermark, Silver notebooks ported, Gold star schema rebuilt on Delta | 1-18 |
| 6b — Real-time | Event producer, Eventstream, Eventhouse, update policies, materialized views, retention and caching policy, KQL dashboard, Activator alerting | 19-32 |
| 6c — Semantic layer on Fabric | Direct Lake model, RLS, reports republished, performance tuning and measurement | 33-42 |
| 7 — AI | Forecasting, RAG copilot, NL-to-query agent, evaluation harness | 43-52 |
| 8 — Governance and CI/CD | Git integration, deployment pipelines, sensitivity labels, monitoring, cost analysis, runbook | 53-60 |

This makes Phases 2-5 load-bearing: they must be complete enough that Phase 6
is a port, not a redesign. The schedule gain from completing Phases 0 and 1
in one day is allocated to depth in Phases 2-5, not to starting Phase 6 early.

## Review trigger
Revisit if a Phase 2-5 design question cannot be answered without
Fabric-specific behaviour, if Microsoft changes trial terms, or if Phases 2-5
finish with the port estimated under 10 days.
